HEXAGONAL ARCHITECTURE:

Mostrar estrutura de pastas:

services/users/src/
├── Core/                          ← LÓGICA DE NEGÓCIO
│   ├── Domain/                    ← Aggregates, ValueObjects, Events
│   │   ├── UserAggregate.cs
│   │   ├── Email.cs (ValueObject)
│   │   └── Password.cs (ValueObject)
│   └── Application/               ← CQRS: Commands & Queries
│       ├── UseCases/
│       │   ├── Commands/RegisterUserCommand.cs
│       │   └── Queries/GetUserByIdQuery.cs
│       └── MessageBrokerHandlers/ ← Integration Events
└── Adapters/                      ← INFRAESTRUTURA
    ├── Inbound/
    │   └── Api/                   ← FastEndpoints (REST)
    └── Outbound/
        └── Infrastructure/         ← Marten, Redis, Service Bus

MICROSERVIÇOS:

Serviço	Responsabilidade	Tecnologia Principal
Users	Autenticação, autorização JWT, gestão de usuários	Event Sourcing (Marten Event Store)

CQRS + EVENT SOURCING:

"O serviço de Users implementa Event Sourcing completo. Todo estado é reconstruído através de eventos, garantindo auditoria completa e time travel."

Mostrar exemplo visual:

Event Store (mt_events table):

│ ID │ Stream ID │ Version │ Type             │ Timestamp      │
├────┼───────────┼─────────┼──────────────────┼────────────────┤
│ 1  │ user-123  │ 1       │ UserRegistered   │ 2026-01-01 10h │
│ 2  │ user-123  │ 2       │ EmailUpdated     │ 2026-01-02 14h │
│ 3  │ user-123  │ 3       │ PasswordChanged  │ 2026-01-03 09h │
└────┴───────────┴─────────┴──────────────────┴────────────────┘

Benefícios:
✅ Auditoria completa (LGPD, compliance)
✅ Reconstrução de estado em qualquer ponto no tempo
✅ Debugging facilitado (replay de eventos)
✅ Natural fit com CQRS

DOMAIN-DRIVEN DESIGN:

"Aplicamos DDD tático: Aggregates para consistência transacional, Value Objects para validação de domínio, e Domain Events para comunicação assíncrona."

Exemplo de Value Object:

public record Email
{
    private Email(string value) => _value = value;
    
    public static Email From(string email)
    {
        // Validação no próprio objeto
        if (!EmailRegex.IsMatch(email))
            throw new DomainException("Email inválido");
        return new Email(email);
    }
}

OUTBOX PATTERN:

┌─────────────────────────────────────────────────────┐
│ OUTBOX PATTERN: TRANSACTIONAL MESSAGING             │
├─────────────────────────────────────────────────────┤
│                                                      │
│ 1. Begin Transaction                                │
│ 2. Update Aggregate (Marten)                        │
│ 3. Write Event to Outbox Table ← MESMA TRANSAÇÃO    │
│ 4. Commit Transaction                               │
│    ─────────────────────────────                    │
│    [Transaction Boundary]                           │
│    ─────────────────────────────                    │
│ 5. Background Worker lê Outbox                      │
│ 6. Publica no Service Bus                           │
│ 7. Marca como entregue                              │
│                                                      │
│ ✅ Garantia: At-least-once delivery                 │
│ ✅ Mensagem NUNCA é perdida                         │
│ ✅ Mesmo que Service Bus esteja indisponível        │
└─────────────────────────────────────────────────────┘

SAGA PATTERN (Fluxo de Compra):

"O fluxo de compra de um jogo demonstra o padrão Saga orquestrado via eventos."

Mostrar sequência:

SAGA: COMPRA DE JOGO

1️⃣ Games Service
   └─► Publica: GamePurchaseRequestedIntegrationEvent
       {
         userId: "123",
         gameId: "456",
         price: 59.90
       }

2️⃣ Payments Service
   └─► Recebe evento
   └─► Processa pagamento
   └─► Publica resultado:
       ✅ PaymentApprovedIntegrationEvent
       ❌ PaymentFailedIntegrationEvent

3️⃣ Games Service
   └─► Recebe PaymentApproved
   └─► Adiciona jogo à biblioteca do usuário
   └─► Usuário vê jogo disponível

   OU

   └─► Recebe PaymentFailed
   └─► Libera reserva
   └─► Notifica usuário

AZURE SERVICE BUS TOPOLOGY:

Tópicos e Subscriptions:

user.events-topic
├── games-user-subscription (SQL filter: eventType = 'UserRegistered')
└── payments-user-subscription

game.events-topic
├── payments-game-subscription (SQL filter: eventType = 'GamePurchaseRequested')
└── analytics-game-subscription

payment.events-topic
└── games-payment-subscription (SQL filter: eventType IN ('PaymentApproved', 'PaymentFailed'))

Benefícios:
✅ Pub/Sub pattern (desacoplamento)
✅ Filtering server-side (economia de rede)
✅ Dead Letter Queues (retry automático)
✅ At-least-once delivery garantido

OTIMIZAÇÃO DE RECURSOS (Case de Sucesso):

"Encontramos um problema: pods não conseguiam ser agendados devido a pressão de memória. Usamos dados reais dos testes para otimizar."

Mostrar processo:

🔴 PROBLEMA INICIAL:
├── Memory requests: 700Mi por pod
├── Node capacity: 8GB (5.7GB usable)
├── Pods por node: 3-4 pods
├── Utilização: 101% (saturação!)
└── Resultado: Pods em Pending, HPA não conseguia escalar

🔄 ANÁLISE (via kubectl top pods):
├── Uso real: 400-500Mi por pod
├── Over-provisioning: 40-50%
└── Decisão: Reduzir requests com margem de segurança

✅ SOLUÇÃO IMPLEMENTADA:
├── Memory requests: 512Mi (-27%)
├── Memory limits: 1400Mi (-22%)
├── Pods por node: 5-6 pods (+50% densidade)
├── Utilização: 60-75% (saudável!)
└── Resultado: HPA funcional, auto-scaling comprovado

💰 IMPACTO:
├── Redução de custo: ~27%
├── Melhor utilização de recursos
└── Escalabilidade garantida
